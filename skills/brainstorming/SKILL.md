# 设计澄清（Brainstorming）

将影响实现的未决选择快速收束为用户确认的设计。普通技术实现取舍由执行者自主决定；真正改变产品行为、架构方向、兼容性或外部授权的选择交由用户确认。

## 1. 查证并澄清关键选择

1. **先查证再发问**：检索相关代码、文档与历史记录，自行消除可通过查证解决的歧义。
2. **给推荐与取舍**：针对仍需拍板的关键选择，提供有依据的推荐方案、核心代价及替代方案的适用条件。每次聚焦 1–3 个实质问题，交互形式配合用户与当前 harness。
3. **明确完成标准**：说明可观察的成功行为；优先引用现有检查，区分“可立即验证的功能行为”与“需通过实验/运行观察的长期效果”。
4. **确认即闭环**：用户拍板后直接采用该决定推进后续工作，同范围授权持续有效。

## 2. 设计文档（SPEC）沉淀

当用户明确要求，或多项关联决定需共同审阅与长期留存时，保存设计文档（默认路径 `docs/superpowers/specs/YYYY-MM-DD-<topic>-design.md`，项目有既有规范或可承载文档时优先复用）：

- **内容聚焦**：围绕目标问题、方案设计与取舍理由、协同职责及完成标准展开；接口、迁移与错误处理按实际需要编写。
- **单一规范源**：Markdown 是唯一可编辑源。如需 HTML 阅读视图或可视化辅助，参考 [呈现指南](references/presentation.md)。
- **可开工自检**：区分“已拍板决定”与“待决取舍”。若设计稿需交接给其他执行者且存在理解歧义风险，可参照 [审阅说明](spec-document-reviewer-prompt.md) 做一次可开工检查。

## 3. 退出与衔接

关键选择确认后立即进入实施，按剩余工作复杂度走最轻路径：
- 常规开发任务直接按 L1/L2 实施；
- 涉及复杂依赖、跨模块迁移顺序或多代理协作交接的 L3 任务，转入 `writing-plans` 编写执行计划。
