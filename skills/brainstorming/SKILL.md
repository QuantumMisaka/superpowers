# 设计澄清（Brainstorming）

本 Skill 仅处理 L3 中尚未解决的产品、架构、接口、安全或跨系统决策。

**设计确认后再执行实现。** 未确认前不写代码、不 scaffold、不调用实现 skill。

多文件机械迁移若目标、映射和验证都已确定，直接进入 writing-plans；它需要实施分解，不需要重新发明产品设计。

仅当错误假设会改变公共行为、架构边界、迁移策略或交付结果时提出阻塞问题。先从仓库和已有约定消除可查证歧义。

在此边界内，把粗略想法变成用户已确认的设计决策。默认走 Grill 快路径，需要固化设计时升级为完整 spec 产出；问题数是负担控制，不是完成配额。

## §1 Grill（默认路径）

1. **先探索项目上下文**（代码/文档/commits/现有模式），可查事实不转交用户；长调查仍提供简短进度。
2. **仅询问尚未解决且影响实现的决策**，通常 1-3 个；没有未决项则不问，确有更多实质决策时说明原因并继续，不为压到三题而猜测：
   - 一次聚焦一个真正的取舍，不把目的、范围、方案和验收捆成一个“对吗”。
   - 给出有依据的推荐、主要代价，以及什么条件下另一方案更合适；尊重用户自填答案，交互形式服从当前 harness。
   - 区分已查明事实、实施判断和需要用户决定的产品选择；后者未经确认不进入实现。
   - 提供能观察的成功标准。已有命令可引用；测试尚未存在时描述待验证行为，不虚构可执行命令。
3. **用户确认后，判断是否需要设计文档：**
   - 产出 HTML spec：用户显式要求、多项设计决策需共同审阅、公共 API/schema/持久化数据或安全边界变更、或跨系统约定需长期保存 → 直接产出 HTML spec（§2）；用户已明确要求仅在对话确认时尊重该选择，不再询问是否产出。
   - 不产出 spec：目标、映射和验证已确定的机械实施、决策已在对话中内化（用户说出了答案）、或用户选择仅对话确认 → 进入 `writing-plans`，记录对话中的设计与授权来源。
4. 若产出 spec → §2 完整设计流程。L3 即使省略 spec 也保留 PLAN；设计确认本身不等于执行授权。用户已授权按该方案执行时，不重复索取同一范围批准。

## §2 完整设计流程（升级路径）

按 §1 步骤 3 判断需要 spec 时执行。已有探索与已批准决策直接复用，只处理新增或变化部分。（依据：2026-09-06 本人批准四处流程精简）

### 流程

1. **探索与分解** — 若想法跨多个独立子系统，先分解为可独立交付的子项目，对第一个子项目走设计流程。
2. **收束未决方案** — 仅在仍有实质选择时给 2-3 方案、tradeoff 和推荐项。已选方案直接写入，不为文档重开选择。
3. **组织设计** — 按复杂度缩放，覆盖目标、非目标、架构、组件、数据流、错误处理、测试、rollout 和开放决策；将需要本人判断的新增或变化项集中标出。
4. **写 HTML spec** — 使用 [design-template.html](design-template.html) 到 `docs/superpowers/specs/YYYY-MM-DD-<topic>-design.html`，保留适用段落，不为填模板创造设计。
5. **自审** — 占位符扫描、内部一致性、范围检查（单个 plan 能否覆盖）、歧义检查。发现问题直接修。
6. **交付具体产物** — 给出路径及仍待决定的变化。存在未批准决策时，对这些决策进行一次集中审阅；纯粹固化已批准设计时不追加逐段或全文批准。
7. **过渡** — 设计决策齐备后调用 `writing-plans`，记录设计和执行授权来源；已有同范围执行授权则继续，仅缺执行授权时提交具体计划供批准。新增破坏性迁移或安全边界不能由旧批准代替。

### 设计原则

- 拆分为单一职责的小单元，通过明确接口通信，可独立理解和测试。
- 在现有代码库中遵循已有模式；影响当前工作的已有问题可作为设计的一部分改进，但不做无关重构。
- 每个单元能回答：做什么、怎么用、依赖什么。

## §3 轻量对齐（有界但略欠规格）

比 Grill 更轻：变更有界但有一处不确定。

1. 先查项目上下文。
2. 用几行说明变更、约束和成功检查。
3. 只询问这处未决取舍（附推荐与代价）；若发现更大决策面，回到 §1，不猜测剩余选择。
4. 路径明确时进入 `writing-plans`。仅当查证后已不符合 L3 判据，才记录降级理由并按 L1/L2 入口执行。

无需设计产物，除非用户要求或讨论中发现更大设计不确定性。

## 顺序

设计澄清在 `using-superpowers` 路由中的位置：

1. 路由选定"设计澄清"
2. 执行 §1 Grill（或 §3 轻量对齐）
3. 需要 spec 时执行 §2
4. L3 过渡到 `writing-plans`；依据 2026-09-05 授权审查，省略 spec 不省略计划载体。
