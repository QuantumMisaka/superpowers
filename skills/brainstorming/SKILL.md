# 设计澄清（Brainstorming）

将影响实现的未决选择快速收束为用户确认的设计。普通技术实现取舍由执行者自主决定；真正改变产品行为、架构方向、兼容性或外部授权的选择交由用户确认。

## 1. 查证并澄清关键选择

1. **先查证再发问**：围绕期望结果检索相关代码、使用方与历史记录，自行消除事实歧义，并列出仍需用户确认的目标、范围、验收与约束。涉及替换或移除既有设计时，查明原约束及其当前适用性。
2. **给推荐与取舍**：针对仍需拍板的需求或关键选择，结合已有偏好，提供有依据的推荐方案、核心代价及有实质差异的替代方案。每个问题只聚焦一个取舍，不把目标、范围、方案与验收捆成一个问题；每次 1–3 个实质问题，交互形式配合用户与当前 harness。

   比较重要方案时，沿实际依赖推演对调用方、用户行为和长期维护的影响，将职责、命名和隐含约定带来的理解成本纳入取舍。找出最可能推翻推荐方案的反例或边界条件，用代码、历史证据或小实验核实；尚待观察的影响说明验证方式。现有方案受限时，可借鉴其他领域的机制，并核对其成立条件是否适用于当前问题。

   例如，用户希望增加重试来解决任务丢失：先追踪提交、确认与执行过程；若发现确认丢失导致重复提交，就比较幂等处理与重试的配合方式，并用重复请求验证关键前提。

3. **明确完成标准**：说明可观察的成功行为；优先引用现有检查，区分“可立即验证的功能行为”与“需通过实验/运行观察的长期效果”。
4. **确认即闭环**：用户拍板后直接采用该决定推进后续工作，同范围授权持续有效。

需要独立比较方案时，可按[角色选择](../using-superpowers/references/role-selection.md)委派 `design-analyst`，由主代理结合用户偏好收束实质取舍。

## 2. 设计文档（SPEC）沉淀

当用户明确要求，或多项关联决定需共同审阅与长期留存时，保存设计文档（默认路径 `docs/superpowers/specs/YYYY-MM-DD-<topic>-design.md`，项目有既有规范或可承载文档时优先复用）：

- **内容聚焦**：围绕目标问题、方案设计与取舍理由、协同职责及完成标准展开；接口、迁移与错误处理按实际需要编写。
- **单一规范源**：Markdown 是唯一可编辑源。如需 HTML 阅读视图或可视化辅助，参考 [呈现指南](references/presentation.md)。
- **可开工自检**：区分“已拍板决定”与“待决取舍”。若设计稿需交接给其他执行者且存在理解歧义风险，可参照 [审阅说明](spec-document-reviewer-prompt.md) 做一次可开工检查。

## 3. 退出与衔接

关键选择确认后立即进入实施，按剩余工作复杂度走最轻路径：
- 常规开发任务直接按 L1/L2 实施；
- 涉及复杂依赖、跨模块迁移顺序或多代理协作交接的 L3 任务，转入 `writing-plans` 编写执行计划。
