# 设计澄清（Brainstorming）

把未决选择收束为用户确认的设计。先查仓库与已有约定，普通技术取舍可自主决定；真正影响产品、架构、兼容或授权的选择交由用户确认。未确认前不实施受影响部分；独立且已授权的工作可以继续。

加载本技能不决定任务等级。没有未决设计就复用已有决定；已知映射的机械迁移也不需要重新设计。

## Grill：只问需要决定的事

1. 探索相关代码、文档和历史，先消除可查证歧义。
2. 对仍影响实现的选择给出有依据的推荐、主要代价和替代方案适用条件。一次聚焦一个取舍，通常一至三问即可；问题数不是配额，有更多真实选择时如实说明。交互形式服从用户与当前 harness。
3. 说明可观察的成功标准。现有检查可以引用，尚无测试时描述行为，不虚构可执行命令。
4. 确认后直接采用该决定，不因换阶段或写文档重复询问。

例如：兼容可选参数的默认行为需要在 A/B 中选择，问清这一项后即可按 L2 实施；不会因为问过问题就要求完整设计和计划。

## 是否需要设计文档

用户明确要求，或多项关联决定确需共同审阅、长期约定需要保存时，使用 [design-template.html](design-template.html) 在 `docs/superpowers/specs/` 写 HTML spec。优先补充已有规范；公共 API、schema 或跨模块字样本身不要求新文档。

按实际需要说明目标、范围、重要接口、错误处理与验收；有实质替代方案才比较，不为填模板创造组件或决策。自审范围、一致性和未决项。纯粹固化已批准设计直接交付；新增决定集中提交用户判断。

用户选择仅在对话确认时尊重该选择。设计确认与执行授权分别看已有请求，同范围已有授权不再索取。

## 退出与后续

问题解决即退出。依据剩余工作选择最轻路径：有界实施回到 L1/L2 直接执行；确需统筹依赖、迁移顺序、交接或恢复进度的 L3 用 `writing-plans`，省略 SPEC 也保留 PLAN。
已有方案与实施授权时继续；缺少实质决定或执行授权时，只询问相关缺口。写过设计稿、存在清单或读取本技能都不自动触发计划流程，也不要求降级证明。
