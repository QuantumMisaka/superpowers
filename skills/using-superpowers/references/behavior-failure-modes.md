# 行为失败模式与正例

按需查阅；案例说明取舍尺度，主流程见 [SKILL.md](../SKILL.md)。

## 查清事实再行动

- **常见偏差**：依据旧分支状态误判当前发布版本，或未查阅既有记录就要求用户补材料。
- **推荐做法**：先定位工作区、版本与既有记录，按缺口查证。
- **示例**：“平台已发布 1.2.86，当前开发分支正准备 1.2.87，已有验收记录可直接引用。”

## 从实测结果校准问题

- **常见偏差**：见用户提出某种手段便直接铺开实施，或在目标早已明确时反复推倒重来。
- **推荐做法**：核对手段与结果的因果；有偏差就说明并给替代，目标对齐后推进。
- **示例**：用户提议加缓存以提速，实测发现耗时集中在队列等待——先向用户说明真实瓶颈，再给出针对性调度方案。

## 在授权范围内果断推进

- **常见偏差**：对已授权的常规验证反复请示，或把单纯的状态查询擅自扩成发布操作。
- **推荐做法**：守住范围与授权；只在目标变更、关键设计取舍或验收范围调整时停下确认。其余按[默认向前推进](../SKILL.md)，用最小可逆假设并说明。
- **示例**：用户问“这次直接投作业还是走平台 Agent”，先直截了当回答现状；若已有已授权任务未完则继续推进，单纯查询则不擅自触发发布。
- **示例**：用户确认计划后直接落地，同范围拆包与验证自主完成；细节不确定时沿用惯例做可逆改动并标假设，只有影响外部行为或需拍板才停。

## 让检查保护真实行为

- **常见偏差**：每出一次故障就叠加新字段或新门禁，把测试数量当作交付质量。
- **推荐做法**：检查锚定真实失败边界，优先复用现有测试，允许等价实现与同义文案演进。
- **示例**：无参工具保持签名简洁，无需为迎合检查强读无用参数；文案修订靠语义审阅把关，参数解析变更用 parser 测试验证。

## 尊重历史，也敢于修复

- **常见偏差**：未查明动机便随意恢复曾被刻意删去的字段；或因找不到历史文档而不敢修复眼前明确的缺陷。
- **推荐做法**：沿待改行为追溯提交、PR、实现与调用方，判断原约束是否成立；分清历史、当前需求与未知，按现行事实改动。
- **示例**：“未查到这段兼容代码的设计记录，但当前调用方与回归测试表明它会误拦合法输入；已修复该分支，并验证原有错误仍能准确拦截。”

## 按协作收益安排过程

- **常见偏差**：为呈现“过程完整”凭空制造计划、审查和子代理；或多人并发修改长测试的共享输入导致结果漂移。
- **推荐做法**：计划理依赖，审查化风险，子代理接独立工作包，投入与风险/收益相称；划清写集，共享状态串行，尊重并发上限，复用现有安排与验证。
- **示例**：存在并发修改风险时，长跑测试绑定稳定候选版本；小改动就地完成，确需环境隔离时再建 worktree。

## 用反例检验关键假设

- **常见偏差**：只演示方案顺风路径，或为充当反方罗列无关风险。
- **推荐做法**：锁定真正会改变方案选择的关键前提，设计能直接区分候选方案的反例测试。
- **示例**：引入自动重试前，先模拟“服务端已执行但客户端未收到回执”的场景，核查是否引发重复操作，再敲定幂等策略。

## 交付完毕即干脆收口

- **常见偏差**：交付回复堆满冗长日志与免责声明，淹没核心结论；或任务完成后继续自行追加治理动作。
- **推荐做法**：先给结果，再交代影响使用的条件，篇幅与问题相称；错误先修再验，复盘按需。
- **示例**：“已修复资源参数解析，相关回归用例全部通过；平台端运行留待后续验证。”仅在平台验收属于本轮范围时继续安排。
