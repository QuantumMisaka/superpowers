# 从复盘到改进

适用于用户发起的阶段复盘，或重复故障、高频返工暴露共性机制的场景。核心目标是切实降低下一次交付的失败率与等待成本，结论直接沉淀进项目既有记录。

## 1. 界定问题与证据

先明确复盘的时间窗口、期望改善的目标与核心指标。例如调查“最慢的 PR”时，先拆清交付周期、CI 耗时与代码运行性能，再按环节细分实现、审查等待、测试与外部依赖耗时。结合 PR、提交、故障与回滚记录，选取典型失败与可比成功案例展开对照；仅在定位需要时做全量扫描，并如实注明覆盖面与证据缺口。

## 2. 识别可检验的共同机制

沿着事件时间线还原问题链条，区分偶发触发条件与深层共同成因。用成功案例、反例或最小实验检验假设，确认哪些既有约束依然生效；证据尚不足以定论时，设计最能区分候选原因的下一步观察。

## 3. 把改进落在根因位置

优先从实现逻辑、接口契约或默认行为中根除成因：稳定且可自动判定的缺陷交给自动化检查，项目专属约束写入项目文档，跨任务反复出现且需要人工判断的方法沉淀进对应 Skill。改进优先复用既有入口，并同步合并或清理已被取代的旧约束。

例如，若多次回滚均源自重试触发重复写入，应优先在写入边界实现幂等并验证故障路径；当跨项目证据表明该判断普遍容易遗漏时，再补充进设计或审查指引。

## 4. 验证改进实效

为每项改进措施写明预期收益、核验方式与责任落点：当轮可见的行为改动就地验证，需长期使用方能显现的效果在后续同类任务中对照观察。复盘收尾时输出有据结论与最高优先级的改进行动；已获授权的改进直接推进，涉及目标、架构或授权调整的事项按入口的双相协作契约交用户确认。
