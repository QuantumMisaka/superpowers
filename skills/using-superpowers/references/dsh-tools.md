# dsh / ds-bot 原生协作适配

适用于 dsh Web 的 ds-bot 团队。2026-10-23 核对 dsh 0.2.1-rc.2、ds-bot 0.2.0；旧0.1.6实例仍可能运行，以下按版本区分派工语义，以实际工具 schema 为准。CLI 单次任务不假定拥有这些团队工具。

## 入口与职责

Main Bot 读取 using-superpowers，协调跨项目目标、依赖与成员创建。单项目由长期负责人在项目群持有交付与验收责任；简单单项目团队可由Main兼任。项目负责人承担任务分级、派发和最终验收。L1/L2/L3、设计、实现和验证沿用共享技能，不另设流程。简单任务由当前项目负责人直接完成；有独立工作包时按需使用专业成员。

专业 Bot 按委派范围读取项目规则、对应角色技能及必要专业技能，不重复主代理入口路由。主代理给出任务、文件归属、相关接口、验收依据和返回要求；成员报告实际证据与需要主代理决定的问题。稳定职责与关键边界写入 Bot instructions，详细方法引用技能，临时任务通过消息交付。

先 list_bots 再选择成员。复用上下文相关的 Bot；无关任务或需要独立判断时考虑新建。创建前读取适用角色技能，将关键职责写入 instructions，brief 说明本次目的。原生 create_bot 仅 Main 可用；其他成员需要新岗位时向 Main 提出。不要把角色技能名当成已注册的 Bot 或模型。

## 与 L1/L2/L3 联动的默认路由

等级定义仅使用 using-superpowers，不因模型、Bot数量或群聊升级等级。当前项目负责人先分级，再挑选实际需要的工作阶段；开工用一句话说明级别、复用的依据和拟派角色，无需再次索要同范围授权。

| 等级 | 默认执行 | GPT及独立成员 |
|---|---|---|
| L1 | 项目负责人直接完成相称检查，不建SPEC/PLAN或固定团队 | 仅项目明确要求、用户指定或具体风险需要独立判断时派发 |
| L2 | DeepSeek按需初调、承接已有方案并实现验证 | GPT处理影响方案的关键判断；满足requesting-code-review条件时做独立审查 |
| L3 | 保留项目PLAN，负责人管理交付、Main协调跨项目依赖；DeepSeek初调并持续承接任务包 | GPT负责方案与独立审查，设计咨询和独审分会话；已有有效成果核对后复用，不自动重跑七阶段 |

2026-10-23本人确认上述DeepSeek初调/承接、GPT方案/独审分工，覆盖旧版“缺失调研优先GPT”的默认安排。本人已授权此dsh默认路由在适用任务中使用现有GPT执行器。角色/模型/effort仍以当前目录及实际工具为准；GPT路由不可用应说明受影响阶段，不能把DeepSeek输出冒称GPT，不能仅为赶进度绕过必要审查。跨模型偏好只属于此适配，不改变Codex等其他入口配置。

调研解决具体未知项；方案复核重点是“依据这些输入能否开工、还有哪些真实缺口”。沿用 brainstorming 的按需可开工检查：普通实现选择自主决定，有关键新决策才回用户。仅有需要修订的内容时才派文档完善员；不创建没有独立产出的岗位。

每个选中的独立专业阶段使用新的聚焦会话/任务，给出必要事实、文件归属和验收依据，避免完整主会话复制。修复轮可续用原实现者，独立复验保持独立。多个无依赖工作包可以并行，依赖阶段待实际结果后再派发；这一规则不要求把每个小操作拆成一个Bot。

微型任务调查/计划只需短结论；项目负责人在任务说明中给出相称篇幅与停止条件，达到验收即交接。L2通常复用需求记录，L3复用项目计划；不要为角色数量配套造文档。项目规则、已确认决定与实际证据优先，个人品味只在相关取舍或表达中读取。

用户明确要求完整七阶段时，按[跨模型阶段编排](dsh-cross-model.md)执行；默认路由也可从其中选取所需阶段，省略的阶段标明复用/无需，不声称执行过。

调用外部角色时使用已挂载能力的工具与角色目录。旧home可用已登记的 `workspace_name=team`；多项目工作室使用登记的项目和具名checkout，不能假定所有任务都在team目录。工具受阻时报告缺口；不探查其他home、任务私有输入或凭据来拼接调用。原生workspace-write通常不限制读取范围，聚焦输入需要遵守这条职责边界。

## 项目工作室的任务交接

每个项目有负责群和长期负责人。需要独立交付岗位时，负责人请Main创建任务Bot；临时任务完成后保留记录并退场，持续专业职责可按需保留。任务Bot下的原生子代理或Codex执行不因此变成另一个项目负责人。Main可汇总既有阶段成果与项目依赖，项目原计划仍是权威。

以实际可见工具为准：配置projects且提供 `register_task` / `start_task_role` 的工作室走任务绑定入口；旧home保留原 `start_role`。负责人先登记目标、写入范围、验收条件、实际产物和TaskBot，再在项目群明确派发。任务Bot使用同一task_id下不同execution区分开发、设计咨询和独立审查；短作业用ephemeral，复杂开发显式persistent。审查发现交回原开发execution的最新job续接，使用新的逻辑request_id；同一次请求重试保持原ID。不能用换ID绕过未知执行或重叠写入。

一次启动成功只表示已经派工。收到完成通知后读取真实状态和工件，再推进有依赖的阶段；通知可能重送，先按job_id核对已处理记录。任务Bot负责推进，项目owner负责接受；转交派工方须显式交棒。Bot退场前核对未决请求、外部执行与后续接收人。群级workDir会覆盖成员目录，多仓或多worktree项目群通常不设置统一目录。

交付、阻塞或需要决定时，在原群明确@接收负责人，并说明需要其核验、接手或决定什么。普通Bot广播不保证唤起群admin；已回群不等于接收方已接手。普通进展留群内即可，等待接收时不重新派发同一执行。

独立GPT审查给需求、实际代码/文稿、差异和验证条件，设计会话与作者自评不作为独审前置结论。只读审查遇到需要临时写入的测试，应说明哪些检查无法运行，由有写入授权的执行者或负责人提供可核验运行证据；不为跑测试扩大审查权限，也不把权限拒绝误报为产品缺陷。

新任务与恢复检查点按需要重读personal偏好、工程实践及科研当前主线的源入口。团队记忆用于索引和协作摘要，源文更正优先；来源失效时保留未核新状态。经验改进绑定实际问题、适用条件与验证，在项目文件或对应规范维护者处采用/撤回，不从一次聊天推导全局偏好。严格评测继续使用专门输入边界，普通新Bot或spawn不自动等于严格隔离。

## 工具映射

| 动作 | 原生方式及语义 |
|---|---|
| 发现成员与群聊 | list_bots；成员名单可能变化，不凭记忆猜名字 |
| 创建/调整成员 | create_bot / update_bot；尊重用户已有设置和原生权限 |
| 独立派发与继续 | message_bot，默认 reply_to=me；私聊中向目标私聊派发，0.1.7起在群中调用则向本群成员派发；消息带必要输入与验收要求 |
| 当前私聊任务纠偏 | message_bot 默认 when=now；目标在下一步读取 |
| 无关的新任务 | message_bot when=queue，避免打断现有私聊任务 |
| 结果回收 | 异步回复触发后续处理；有独立工作就继续，无事可做就结束本轮等待回复，不轮询、不重发，不虚构 wait_agent |
| 用户直接听成员汇报 | reply_to=user；结果在成员私聊显示，不会回给派发者 |
| 事项讨论 | create_group / update_group / post_to_group；用精确成员名 @ 调度 |
| 紧急停止 | Main 使用 stop_bot；会影响目标运行任务与队列，不作为日常等待手段 |
| 计划与进度 | 项目已有计划/交接文档；ds-bot 隐藏 DSH goal 工具，不虚构 goal 生命周期 |

模型从当前可用目录选择，默认沿用原生配置。0.2.0的create_bot / update_bot支持effort，模型须支持对应档位；权限仍由用户通过原生UI或已授权配置接口设置。旧版本先核工具schema，不推测参数。角色正文的“只读”是职责约定，不能替代权限。可选外部 CLI 执行器只在任务需要且已授权时使用。

## 项目群协作

单项目旧团队可由Main担任admin、mode=admin；项目工作室默认由相应项目负责人主持，普通Bot也可担任群管理员。用户普通消息先交主持人，由其定向 @成员。@ 是调度动作；只叙述某成员时写名字，不加 @；要求负责人去派发某人时，先向负责人发消息，不在用户群消息里把被转述的成员写成@目标。@all 用于确需全员输入的事项。无新增信息或非本人的问题按原生规则返回 [PASS]，不互发致谢与状态回声。

每个事项群明确目标、共同依据、分工和收敛条件，写入 notice；项目规则仍适用。主持人派发、接回结果、处理分歧并验收，不要求每位成员轮流表态。成员被要求执行时实际完成工作，关键进展和结果在群中报告，不只承诺稍后处理。

create_group会自动加入创建者，不接受work_dir；需要共同目录时，Main建群后调用update_group(work_dir=绝对路径)，再用list_bots核对实际群目录与成员。群目录优先于成员个人目录，不以创建成功的提示代替配置回读。

选择主要执行会话：独立调查/实现/审查可以私信派发；需要用户可见进展或项目共同上下文时在对应群中派发和纠偏。0.1.7起，群内message_bot与@一样在本群派发，目标须是成员；从私聊发起message_bot仍进入目标私聊。0.1.6的message_bot只进入目标私聊，组内任务用@。

从私聊post_to_group发起讨论时应显式@目标成员：发送者不会回答自己的帖子，不能依赖管理员自动接管自己发的无@消息。需要回到发起者时设置report_back=true；默认只在群内显示，可用read_group_chat查看。包括0.2.0在内，report_back都可能只回群轮次摘要或Still working；晚到结果留在群内，不保证再次私聊通知，需另读群记录。0.1.7起改善的是message_bot请求链的依赖跟踪与回传，不能据此推断群长任务已结束。各版本都以实际回传及产物核验判定完成，群轮次结束、已发消息和空闲标记均不足以证明交付。

同时 @ 多名成员适合独立输入；不能靠 @ 顺序保证依赖。若 B 必须基于 A 的结果判断，先只 @A，待实际结果到达后再 @B 并附上结果。独立任务先各自形成结果，再将必要证据带入群中讨论分歧。讨论收敛后主持人把决定、未决项和下一步写回项目文件，按 verification-before-completion 核验后报告；群发言或成员自报成功本身不等于验收通过。0.1.7已移除旧版若干消息计数上限，但轮次仍有控制；实际受阻时汇总状态，不靠重复发送绕过。

## 信息聚焦与隔离边界

Bot 私聊独立；每个 Bot 在每个群也有自己的会话，但沿用该 Bot 的身份设定。首次群会话会带入该 Bot 私聊最近最多 10 条消息摘录；可用 read_own_chat 回查私聊，read_group_chat 回查可见群聊。新群不等于全新干净上下文。

另有 Bot 自有记忆、团队共享记忆和共同文件。0.2.0新增群记忆，默认在该群内读写；成员自身记忆与团队记忆仍进入群会话。群记忆保存项目共同决定，通用角色方法留在自身记忆，跨项目偏好留在团队记忆；旧版写入个人/团队的群事实不会因升级自动搬走。需要独立审查时给出需求、实际变更及证据，避免预灌实现者结论；必要时新建审查 Bot。新 Bot 仍可能读取团队记忆与文件，不宣称严格盲审或安全隔离。严格隔离需求应使用明确的数据/权限边界另行实现。

并行写入明确文件归属，重叠写入串行或隔离工作区；会话分开不隔离 Git index 或项目文件。群权限可覆盖成员个人权限，审查者进群后不能只凭其个人设置声称只读。

项目文件保存目标、计划、决定和验收事实。个人品味按架构取舍、协作或表达需要读取相关部分；稳定且跨任务有用的事实才适合团队记忆，临时假设保留在事项中。

## 工作室交付与反馈

启用绑定任务工具的工作室中，项目负责人核对产物和独立审查后验收；已授权范围内自主收口，不默认等本人逐项批准。交付用 `present` 给实际文件入口并核对读者可见。本轮0.2.0群内调用后未显示文件卡，负责人私聊呈现已实测可打开；群里保留结论与路径，不以工具调用成功替代页面核验。已验收稿件收到局部反馈时，先保全原文，再由owner用 `reopen_task` 绑定原任务、反馈ID及受审文件版本；保留旧验收，完成本次修订与受影响范围的复核后再验收。遇到人工改稿、范围已被接手或执行未知，先核对差异，不改状态绕过。

涉及科学解释的交付，按实际问题选择能核对原始证据与适用条件的审查职责；通用实现检查不能替代科学判断。上级已指定阶段成果时，项目owner在任务登记时用 `link_result` 关联，Main从派生总览读取阶段进度，同一任务多处引用不重派工；可见任务全部ready不等于完整阶段或论文完成。事实源和正式产物仍留原项目，局部反馈不自动提升为个人全局偏好。

## 来源与维护

工具语义核对安装包 ds-bot 的 src/host/{tools,groups,prompt,permissions,chat-index}.js；技能发现核对 @deepseek-ai/dsh-skill-filesystem。此说明随 Superpowers fork 同步，以项目挂载的固定版本消费，不在每个 home 复制另一份规则。发现同名技能覆盖时核对实际解析路径。

用户指定 GPT调研/规划→DeepSeek实施→GPT验收时，使用[跨模型阶段编排](dsh-cross-model.md)；该模式按阶段新建执行会话，普通任务保持上述按需协作。
