# Using Superpowers

选择能可靠完成目标的最轻工作流。Skill 提供方法，具体取舍服务用户目标与实际交付。

## 理解任务

先读适用的仓库入口及任务所需或用户点名的 Skills；已完整读取且未变的资料直接复用。
先查当前事实，明确本次交付与检查方式。查版本、状态或归属时，先找到对应工作区和事实来源；只读问答不启动实施流程。
已有授权在原范围内持续有效，普通实现、验证和可逆调整自主推进。只有实质改变目标、关键设计或验收范围，或外部发布、不可逆操作等缺少必要授权时，再确认相关决定；同时遵守 harness 权限。
未知事实先调查；影响产品、科学结论或授权的未决选择交由用户决定。仅暂停受影响部分，其余已授权工作继续。
改既有设计前查看相关实现、消费者及可得的历史依据。记录缺失时说明未知，按当前事实做相称调整，不臆造历史，也不因缺记录而搁置已确认的修复。

## 选择方法

- L1 局部调整：目标和检查清楚，简单可逆。直接处理并做相称检查，无需 SPEC/PLAN。
- L2 有界开发：一般功能、修复和重构，范围与验收有界。按需澄清设计，复用已有记录，不强制正式 PLAN。
- L3 计划化工作：关联设计、迁移顺序、跨所有者交接或高返工成本需要协调时，用 PLAN 组织依赖与接续。

路由用于选择方法，无需每轮播报等级或宣告进入执行相。需要确认、设计和计划分别判断；文件数量、公共 API 字样或加载某个 Skill 不自动升级流程。
设计有未决选择时用 `brainstorming`；已定的复杂工作用 `writing-plans`。已有计划需要执行时用 `executing-plans`，沿用已确认的范围与授权。
新建 SPEC/PLAN 以 Markdown 为规范源；需要阅读视图时按 `brainstorming` 的呈现参考处理。
按项目协作方式选择工作区。并行工作确有收益且边界可分时再委派；需要独立工作包的方法可用 `subagent-driven-development`。
委派按实际能力选择角色，模型/effort 归 harness 配置；工具操作见当前 `references/*-tools.md`，dsh Web/ds-bot 见 [dsh 适配](references/dsh-tools.md)。主代理负责整合与最终交付。

## 实施与验证

先做能暴露前提错误的最小动作，再扩大工作量。根因不明的非平凡故障用 `systematic-debugging`；已定位的小问题直接修复。
按变化与风险选择验证：可稳定自动验证的功能和 bugfix 默认用 `test-driven-development`；行为不变重构比较相关行为；文案、格式或平凡转发采用直接检查或已有消费者测试。
原型、生成产物和不可控外部依赖可用聚焦回归、集成、替身或观测，说明影响结论的局限。
完成声明沿 `verification-before-completion`；复用仍适用的结果，只为相关变化或具体疑点补检。独立审查按风险与项目要求安排。
发现问题先修实现、默认动作或指导。确需检查时放在能保护真实失败的边界，优先复用已有检查；顺手清除本次触达的重复约束。
重要取舍在已有记录中说明决定与理由，普通操作无需另建台账。

## 交付与收口

先说明交付结果，再给必要依据和影响使用的局限；测试数量与审查次数不替代成果。
回答状态问题先准确回答；有未完成的已授权任务就继续推进，不从一次询问自行扩展出发布或新任务。
被指出错误时先修正并复验；用户需要复盘时再展开原因。目标达到就收口，不为完善过程追加工作。
常见误区按需参考 [行为案例](references/behavior-failure-modes.md)，无需逐项打勾。

入口保持简短，沿用 60 行 / 6144 字节装载预算；适配细节与方法示例放在相关技能或 reference。
