# Using Superpowers

选择能可靠完成目标的最轻工作流。Skill 提供方法，一切取舍服务于用户目标与实际交付。

## 1. 理解任务并确定做法

- 从期望结果出发，先查项目入口、实现与使用方；查版本、状态或归属时定位实际消费的来源。若用户提出的手段解决不了问题，说明依据与可行替代。
- **双相协作契约**：能查的事实自行查。目标、范围、验收或关键约束仍有会改变实施的缺口时，用 `brainstorming` 澄清后再选工作流。影响产品、架构、科学结论或不可逆外部动作的未决选择由用户拍板，只暂停受影响部分；已明确的设计和授权内直接推进。

## 2. 按耦合与返工风险选择工作流

- **L1 局部调整**：目标与检查清楚、简单可逆 → 直接实现并做相称验证。
- **L2 常规开发**：范围与完成标准清楚的功能、修复或重构 → 按需澄清未决点，复用已有设计直接推进。
- **L3 计划化工作**：涉及多方设计耦合、迁移顺序、跨所有者交接或高返工成本 → 先定设计或计划再执行。

按实际需要加载支撑技能：
- 复杂工作需拆解依赖与完成标准 → `writing-plans`（新建 SPEC/PLAN 以 Markdown 为唯一可编辑源）；
- 直接执行既有计划 → `executing-plans`；计划需分阶段委派与验收 → `subagent-driven-development`；独立工作并行收益明确 → `dispatching-parallel-agents`。
- 分工收益明确时，主代理主动按[所需成果选择角色](references/role-selection.md)，优先当前 profile 的匹配角色，负责协调与验收；简单或紧耦合任务直接做。项目能力发现可选 `capability-advisor`。

## 3. 实施与相称验证

- **检验关键前提**：围绕决定方案成败的前提，先做能区分候选解释或推翻关键假设的最小检查，再铺开工作量。根因不明的复杂故障用 `systematic-debugging`；已定位问题直接修复。
- **按影响验证**：用 `test-driven-development` 选择能观察到实际变化的检查。配置改变执行路径，就验证执行路径；仅改展示文字，直接核对展示。
- **治理服务交付**：优先修复实现本身；确需新增检查时放在真实失败边界，并顺手清理本次触达的重复门禁与冗余约束。

## 4. 交付与收口

- **结论先行**：沿用 `verification-before-completion`，先报交付结果与关键证据，会改变使用判断的条件随对应结果说明。
- **按需复盘**：用户要求复盘，或重复故障、返工显示共同机制时，按[复盘指南](references/retrospective.md)确定改进落点；本轮范围内完成修复，独立治理事项另列后续工作。
- **自然收口**：回答状态询问时先准确作答，再继续未完的已授权工作；被指出错误时立即修正并复验。达成目标即收口。
- 常见取舍示例见 [行为案例](references/behavior-failure-modes.md)。
