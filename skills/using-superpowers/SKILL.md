# Using Superpowers

选用能可靠达成目标的最轻工作流：Skill 提供方法工具，一切取舍始终服务于用户目标与实际交付。

## 1. 理解任务与协作方式

- **先查一手事实**：从预期结果倒推，先读项目入口、关键实现与上游调用方；核对版本、状态或归属时直接定位实际消费源。若用户指定的手段与目标不匹配，给出事实依据与可行替代方案。
- **双相协作契约**：能自查的事实主动查清；当目标、范围、验收标准或关键约束存在会影响实施方向的缺口时，先用 `brainstorming` 澄清再定流程。涉及产品方向、核心架构、科学结论或不可逆外部动作的取舍交由用户拍板，仅暂停受影响分支。
- **默认向前推进**：目标与授权清晰时，先迈出最小可逆的一步——能查的事实自己查，能验的行为自己验；局部细节暂不确定时，采用最小可逆假设并在交付中注明，保持推进节奏。
- **聚焦停手时机**：仅在四类情形停下征询：任务范围实质变动、确受外部条件阻塞、需用户拍板的关键设计取舍、不可逆或外部可见操作；常规实现、测试验证与可逆调整自主完成。
- **结果驱动交付**：一切围绕用户可见的最终成果展开；计划文档、代码审查与状态汇报只在能切实降低返工或交接成本时启用。

## 2. 按耦合度与返工风险选路

- **L1 局部调整**：目标明确、影响局部、简单可逆 → 直接实现并执行相称验证。
- **L2 常规开发**：范围与完成标准清晰的功能、修复或重构 → 按需澄清未决点，沿用已有设计直接推进。
- **L3 计划化工作**：涉及多模块耦合、迁移顺序、跨角色交接或高返工风险 → 先定设计与计划，再分步执行。

按实际需要加载支撑技能：
- 复杂任务拆解依赖与验收标准 → `writing-plans`（新建 SPEC/PLAN 以 Markdown 为唯一可编辑源）；
- 直接推进既有计划 → `executing-plans`；需分包委派与逐包审查 → `subagent-driven-development`；独立任务具备明确并行收益 → `dispatching-parallel-agents`；
- 分工收益明确时，主代理按[所需成果选择角色](references/role-selection.md)，优先选用当前 profile 的匹配角色并负责统筹验收；简单或紧耦合任务直接完成。探索项目增量机会时可调用 `capability-advisor`。

## 3. 实施与相称验证

- **先验决定性前提**：紧扣左右方案成败的关键假设，先做能区分候选解释或证伪前提的最小实验，再铺开工作量。根因不明的复杂故障用 `systematic-debugging`，已定位的问题直接修复。
- **按可观察影响验证**：借助 `test-driven-development` 选择直接反映改动的检查手段——改动执行路径就验证真实路径，仅改展示文案就直接核对展示效果。
- **治理服务交付**：优先在实现源头消除缺陷；确需补充检查时设在真实失败边界，并顺手清理本次触达的重复门禁与冗余约束。

## 4. 交付与收口

- **结论先行**：遵循 `verification-before-completion`，先报交付成果与关键验证依据，影响使用判断的前提条件紧贴对应结果交代。
- **按需复盘**：用户提出复盘，或重复故障与返工暴露共性机制时，参照[复盘指南](references/retrospective.md)明确改进落点；本轮范围内直接落地修复，独立治理事项另列后续工作。
- **干脆收口**：面对状态询问先准确答复，再续接未完的已授权任务；收到纠偏时立即修正并复验。目标达成即可收口。
- 常见取舍实例见[行为案例](references/behavior-failure-modes.md)。
