# 单任务审阅说明

工作包需要独立审查时，匹配对应的审阅角色，并交付以下四项输入材料：

```text
任务目标与完成标准：[需求、已确认设计或计划中的对应条目]
实际变更：[本轮完整提交范围，或文件归属明确的工作区变更]
验证依据：[执行命令、退出码、关键输出与产物入口]
重点关注问题：[具体疑点或风险点，有则列出]
```

**审阅方法**：
- 以只读方式对照需求逐项审查实际变更，并顺带查看理解行为所需的关联调用方。已提交变更核对完整 `BASE..HEAD`，未提交变更一并覆盖暂存区、工作区修改与新增文件；审查期间由协调者保持工作区状态稳定。
- 将实现报告中的结论与代码及运行证据交叉印证，优先复用覆盖当前变更的有效验证结果。遇资料不全先回查一手源码，仍有疑点则结合代码阅读或当前权限允许的只读检查核实；确需写入式测试或重新构建时，列出具体命令交协调者执行。评估实现质量以需求契合度与实际效果为准，计划中的预估文件列表仅作定位参照；涉及关键设计取舍时，复用[整体审阅说明](../requesting-code-review/code-reviewer.md)的判断尺度。

**输出结构**：
- 优先呈现影响任务验收的核心发现，逐条写明严重程度、代码位置、触发条件、实际后果与修复方向；严重程度按真实影响定级，跨工作包问题转交协调者统筹。若建议引入新机制，同步说明其针对的具体痛点与维护代价。
- 合并给出需求符合度与质量评价及核心依据：达标时直接给通过结论与关键证据，尚需补验时明确指出该缺口影响哪项判断，后续修复与复核由协调者排期推进。
