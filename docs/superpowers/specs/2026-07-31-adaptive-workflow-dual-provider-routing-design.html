摘要

当前 Codex 配置同时服务 OpenAI GPT-5.6 系列和阿里云百炼 qwen3.8-max-preview。现有 Superpowers fork 已为 Qwen 缩短并中文化工作流，但部分面向 GPT 的 Skill 发现、读取和工作流交接契约随之弱化； 同时当前五个 Agent 角色只适合“随父进程继承模型”的单 Provider 运行方式。

本设计建立一套与模型无关的三级 Superpowers 工作流，并将 Agent 的任务职责与模型选择分离。小而明确的改动敏捷完成；有界行为变化使用相称的调查、 测试和复核；存在架构歧义、高风险边界或多任务协调时进入计划化开发。 GPT 与 Qwen 的角色通过 Provider profile 分层注册：OpenAI 主进程原生选择 GPT 子 Agent，Bailian 主进程可原生选择 Qwen 或 GPT 子 Agent；GPT→Qwen 通过稳定文件交接完成。 角色编组按已观察到的优势非对称设计： GPT 侧偏工程实现与代码审查，Qwen 侧偏大上下文归纳、进度与文档工作，同时保留两侧的日常实现能力。

核心原则：选择能够可靠完成目标的最轻工作流；按歧义、行为风险、跨模块协调和返工成本升级。

Provider 原则：按任务能力选择 Provider，而不是跟随主进程；普通实现可互换，复杂工程与代码审查偏 GPT，大上下文、进度和文档工作偏 Qwen。

目标与非目标

目标

  • 让局部、明确、可逆的小修改无需设计文档或多 Agent 仪式即可完成。
  • 让 bug 和行为变化获得与风险相称的根因调查、回归测试或 TDD 证据。
  • 让架构、公共接口、持久化数据、安全姿态和多任务开发进入明确的设计与计划门禁。
  • 恢复 Skill 行动前路由、读取当前版本、用户与仓库指令优先、工作流升级和交接等遵循契约。
  • 以目标、输入、输出和验收证据描述流程，减少道德化、对抗式和泛化禁止语言。
  • 在 Bailian 主进程暴露 GPT/Qwen 两个互补能力组，在 OpenAI 主进程只广告已验证的 GPT 原生路由。
  • 以真实分方向 smoke test 启用 Qwen→Qwen、Qwen→GPT，并为 GPT→Qwen 提供可靠文件交接。

非目标

  • 不自动把当前 fork 整体同步到 Superpowers 上游 v6.2。
  • 不为模型能力建立未经评估的固定刻板路由，例如“所有中文任务都必须用 Qwen”。
  • 不让普通小任务默认同时运行 GPT 和 Qwen 做重复工作。
  • 不在本次实现中引入嵌套 codex exec 作为原生子 Agent 的替代品。
  • 不改变项目级 AGENTS.md、sandbox、approval 或外部副作用授权边界。

三级工作流

级别可观察条件交付流程默认不需要
L1 敏捷修改 目标与验收明确；局部、可逆；不改变公共接口、数据或架构；无高风险外部副作用。 查局部规范 → 最小修改 → 聚焦验证 → 汇报证据。 Plan mode、设计文档、正式实施计划、多 Agent、全套 TDD。
L2 有界行为开发 功能、bug 或重构边界清楚；协调范围有限；无需重新决定架构。 bug 先定位根因 → 对话内短 checklist → 回归测试或 TDD → 受影响范围验证 → 必要时 task review。 正式 spec、跨任务计划、final review。
L3 计划化开发 架构或业务决策未解决；公共 API/schema/持久化数据/安全姿态变化；多子系统或多任务；返工代价高；需要中断恢复。 Plan mode 与设计澄清 → 必要时 spec → writing-plans → 按任务 TDD/实现/复核 → 跨任务 final review。 无条件完整产品 spec；大而机械的迁移可只写实施计划。

文件数量只作为辅助信号。单文件的公开 schema 变更可直接进入 L3； 多文件但完全机械、可自动验证的迁移可以跳过完整设计，直接形成实施计划。

指令设计

恢复的遵循契约

  1. 会话开始和任务意图变化时，选择与当前任务匹配的最轻工作流。
  2. 命中或被用户点名的 Skill 在受管辖行动前读取当前完整版本。
  3. 用户直接要求、最近层级的 AGENTS.md 和项目约定优先于通用 Skill。
  4. 当调查发现风险或歧义超出当前级别时，说明证据并升级工作流。
  5. 设计、计划、实施和验证之间使用明确交接，不依靠模型记忆补全规则。

语言形式

对输出形状和条件路由使用正向契约：“当条件 X 成立，产出 Y，并用 Z 证明”。 只有真实安全边界、不可逆外部动作和已由行为评估证明会被模型绕过的纪律问题， 才使用窄范围禁止。TDD Skill 保留测试先行的技术顺序，但把“lying”“rationalization” 等人格或道德判断替换为可观察的证据缺口。Verification Skill 说明哪些命令能够支持哪些声明， 验证失败时报告实际状态。

Skill 边界

  • using-superpowers 只负责三级路由、Skill 读取契约和升级条件。
  • brainstorming 只负责 L3 中真正存在的设计决策，不拦截 L1/L2。
  • systematic-debugging 负责未解释症状和根因定位。
  • test-driven-development 负责已选定的行为测试循环，不决定任务是否属于 L1/L2/L3。
  • verification-before-completion 负责声明与 fresh evidence 的对应关系。
  • writing-plans 负责 L3 的多任务实施分解，不重复 spec。

双 Provider Agent 路由

基础 config.toml 始终定义百炼 Provider，并同时注册十二个 Provider-specific 角色。bailian.config.toml 只覆盖主进程默认模型，不再决定可见角色集合。

GPT 工程组gpt_task_reviewerTerra / medium任务级代码细节、回归风险和测试审查。
GPT 工程组gpt_final_reviewerSol / medium跨任务架构、代码一致性和高风险最终审查。

该分工是本地实践假设，而不是模型能力定律。GPT 与 Qwen 的普通实现能力可互换； 默认路由只表达当前观察到的优势，并由后续行为评估、耗时和返工率持续校准。

选择规则

  1. L1 默认由主 Agent 完成。
  2. L2/L3 只有在任务可有界委派、并行收益明确或复核价值足够时派生 Agent。
  3. 复杂工程实现和代码细节审查默认进入 GPT 工程组；普通独立实现可按并发、上下文和成本选择任一工程组。
  4. 大上下文归纳、进度核对、文档审查和 HTML/Markdown 起草默认进入 Qwen 信息组。
  5. 设计阶段由 Qwen 汇总上下文和起草产物，GPT 检查技术可实施性，主 Agent 保留决策。
  6. 实施阶段由 GPT 负责关键路径和代码审查，Qwen 负责上下文密集的独立任务和计划进度核对。
  7. 异构 reviewer 只读取明确的 diff、spec、plan 或 review package，不重新执行完整任务。
  8. 主 Agent 汇总证据、处理冲突并作最终决定。

routine、standard 和 monitor 的共享职责使用标准库校验脚本检查核心契约。 Qwen 信息组使用角色级输入、输出和写权限断言防止职责漂移； qwen_document_writer 只在设计决策已确认后写文档，context/progress/document reviewer 均为只读。

Superpowers 入口 Skill 不写具体 Provider 或模型 ID；Codex 专属路由参考表达本地 GPT 工程组与 Qwen 信息组偏好，但仍只按能力选择，不写具体模型 slug。它使用 routine implementer、standard implementer、 code reviewer、context analyst、progress reviewer、document writer 和 monitor 等能力需求。 Codex 全局配置保留十二个 provider-specific 能力模板；角色文件持有实际 Provider、模型和 reasoning。 默认 profile 激活五个 provider-specific gpt_* 角色并使用 V2；Bailian profile 激活七个 qwen_* 角色、继承五个 gpt_* 角色并使用 V1，最多并发四个子 Agent。角色 TOML 只存放在 agents/gpt/ 与 agents/qwen/，根目录不保留重复别名文件。

由于 Codex agent TOML 没有通用 include 机制，本设计接受十二个短配置文件的有限重复， 以自动校验维持共享契约和专属角色边界，而不引入第三方模板依赖。

测试与验收

静态契约

  • 三级路由条件、升级规则和 Skill 优先级可由 shell contract 检查。
  • TDD/verification 保留关键技术证据词，且不含约定删除的道德化措辞。
  • 十二个 Agent 文件、角色矩阵、必需字段、Provider、模型和 reasoning 可由 Python 标准库解析。
  • 共享工程角色的核心职责保持一致；Qwen 信息角色的输入、输出和写权限满足各自边界。

行为评估

在修改 Skill 前后分别用新鲜 GPT 和 Qwen 会话运行同一组用例：

  1. 明确的单值配置修改：应走 L1。
  2. 小型 bug 且已有测试基础设施：应走 L2 并产生回归证据。
  3. 单文件公开 schema 变化：应走 L3。
  4. 多文件机械迁移：应写实施计划，但无需完整产品设计。
  5. 跨系统新行为且验收不清：应先设计澄清。
  6. 存在匹配 Skill 和最近层级 AGENTS.md：应读取并遵循当前版本与优先级。
  7. 复杂多任务工程实施：GPT 负责关键实现与代码审查，Qwen 负责计划进度和证据核对。
  8. 大上下文设计产物：Qwen 负责资料归纳和 HTML/Markdown 起草，GPT 负责技术可实施性审查。

运行时 smoke test

  • 门禁阶段运行 GPT→GPT、Qwen→Qwen、GPT→Qwen、Qwen→GPT 四个持久化 probe。
  • 每个 probe 都必须确认实际 Provider/模型、可读任务交付和可读结果，而不只相信 Agent 自报身份。
  • 协议门禁分别验证 OpenAI V2 与 Bailian V1，避免把某一协议的失败外推到全部 Provider。
  • Bailian probe 必须确认 Qwen 主模型/effort、multi_agent_version=v1、四并发 Qwen→Qwen，以及 Qwen→GPT 的可读任务和结果。

回归

  • 运行现有 tests/skill-content/run-tests.sh。
  • 运行新增三级路由和 Agent matrix 校验。
  • HTML spec 和 Markdown plan 通过占位符、链接、路径和需求覆盖检查。

实施与回滚

  1. 记录当前 GPT/Qwen 行为基线，不改生产 Skill。
  2. 先实现静态失败测试，再最小改写三级路由和证据型 TDD/verification 文案。
  3. 运行修改后行为评估；只有两个模型都达到验收才继续安装。
  4. 在隔离配置中建立十二角色 matrix 并运行解析测试。
  5. 运行同 Provider 和跨 Provider smoke test。
  6. 按 Provider/协议矩阵部署：OpenAI V2 负责 GPT→GPT；Bailian V1 负责 Qwen→Qwen 与 Qwen→GPT；GPT→Qwen 保留文件交接。
  7. 保留修改前文件快照和完整 diff，验证失败时按文件恢复，不使用破坏性 Git 命令。

上游 v6.2 的 SDD workspace、resume 和 re-review 改进在本次完成后单独审计。 审计必须以本设计的三级路由和双 Provider 契约为前置兼容条件，不直接整体覆盖 fork。

风险与已决问题

风险：Codex 文档确认 custom agent 是会话配置层，但没有给出跨自定义 Provider 子 Agent 的完整官方示例。每个 Provider/协议方向的独立 smoke test 是启用门禁。

风险：十二个角色会增加主 Agent 的选择空间。通过工程组/信息组、明确阶段和单一职责描述降低误选。

风险：当前模型分工来自个人使用感受，可能随模型版本变化。行为评估记录模型版本、耗时、返工和审查命中，允许后续调整默认路由。

风险：Skill 措辞变化可能提高敏捷性却降低纪律遵循。通过 GPT/Qwen 基线、修改后评估和静态契约共同控制。

风险：全局 ~/.codex 不是 Git 仓库。实施时必须生成显式快照、diff 和可重复解析验证。

已决：采用三级工作流、一套模型无关 Skill、十二个非对称 Provider-specific Agent，以及 GPT 工程组与 Qwen 信息组的阶段化协作。

已决：本机实测 Bailian V1 能可靠完成 Qwen→Qwen、四并发 Qwen 子 Agent 和 Qwen→GPT；Bailian profile 正式启用七个 Qwen 角色，并发上限为四。

已决：OpenAI 父会话继续使用 V2 和五个 gpt_* 角色。GPT→Qwen 仍受 V2 加密载荷兼容问题影响，该方向采用落盘 review package。

开放问题：Codex runtime 更新后重新验证 GPT→Qwen；通过前不在默认 GPT profile 广告 Qwen 子角色。

本设计已于 2026-07-31 获得用户批准并实施；运行时证据与历史记录见 validation 索引。
